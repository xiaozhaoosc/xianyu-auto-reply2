## 3. 启动报错修复

### 3.1 故障 A：数据库连接池配置校验失败（致命）

**现象**：backend-web / scheduler / websocket 三个 Python 服务启动即退出，控制台出现 Pydantic 校验错误。

**关键堆栈**：

```text
File ".../common/db/redis_client.py", line 25, in <module>
    settings = get_settings()
File ".../common/core/config.py", line 159, in get_settings
    return BaseConfig()
pydantic_core._pydantic_core.ValidationError: 1 validation error for BaseConfig
db_pool_size
  Input should be greater than or equal to 600 [type=greater_than_equal, input_value='10', input_type=str]
```

**根因**：
- `main` 分支把连接池约束收紧为 `db_pool_size: int = Field(default=800, ge=600)`（`common/core/config.py:53`），`redis_pool_size` 同样要求 `>=600`。
- 本机三个服务 `.env` 仍为旧值 `DB_POOL_SIZE=10`，配置加载时直接校验失败。

**修复**：

| 文件 | 修改 |
| --- | --- |
| `backend-web/.env` | `DB_POOL_SIZE=10` → `800` |
| `scheduler/.env` | `DB_POOL_SIZE=10` → `800` |
| `websocket/.env` | `DB_POOL_SIZE=10` → `800` |

说明：
- `800` 与各服务 `.env.example` 一致；连接池按需建连，不会启动即占满 800 条。
- 三个 `.env` 均为本地未跟踪文件，**不会进入 Git 提交**；换机器/重建环境时需按 `.env.example` 重新配置。
- 若目标 MySQL 的 `max_connections` 较小，可按“所有服务 `DB_POOL_SIZE + DB_MAX_OVERFLOW` 总和 < max_connections”下调，但不得低于 600。

### 3.2 故障 B：服务间 API 令牌未初始化（致命，仅首次/重建库时出现）

**现象**：scheduler、websocket 启动后立刻退出。

**日志证据**（`scheduler/logs/error.log`）：

```text
ERROR | _bootstrap:lifespan:90 - 内部 API 令牌加载失败: 服务间 API 令牌未初始化，请先启动 backend 完成数据库初始化
RuntimeError: 服务间 API 令牌未初始化，请先启动 backend 完成数据库初始化
ERROR | logging:callHandlers:1706 - Application startup failed. Exiting.
```

**根因**：
- `INTERNAL_API_TOKEN` 由 backend-web 启动时生成并写入数据库（`common/utils/internal_token_service.py`）。
- `start_all.bat` 原先同时拉起四个服务，scheduler/websocket 抢先启动时数据库里还没有令牌，`load_internal_api_token` 直接抛 `RuntimeError`。

**修复**（`start_all.bat`）：
在启动 backend-web 后、启动 scheduler/websocket 前，增加最多 180 秒的 `/health` 等待：

```bat
powershell -NoProfile -ExecutionPolicy Bypass -Command "$ok=$false; for($i=0;$i -lt 90;$i++){ try { $r=Invoke-WebRequest -UseBasicParsing -TimeoutSec 2 'http://127.0.0.1:8089/health'; if($r.StatusCode -eq 200){ $ok=$true; break } } catch {}; Start-Sleep -Seconds 2 }; if(-not $ok){ exit 1 }"
if errorlevel 1 echo WARNING: Backend-Web not ready in 180s; Scheduler/WebSocket may fail on internal token init.
```

说明：
- 本次 backend 已成功初始化令牌并持久化到数据库，后续启动即使并行也不会再报该错；该等待主要保护“首次部署/重建数据库”场景。
- `start_all.bat` 为本地未跟踪脚本，改动不会进入合并提交。

### 3.3 非致命日志（可忽略）

| --- | --- |
| `Integer display width is deprecated ...` | MySQL 对 `INT(11)` 等显示宽度的弃用告警，来自建表语句，不影响运行 |

## 5. 风控冷却 SOP（缓风控）

### 5.1 冷却期建议

| 项目 | 建议 |
| --- | --- |
| 冷却时长 | 至少 **48 小时**；若期间再次触发验证，则从最后一次触发重新计时，并延长至 **72 小时** |
| 冷却范围 | 该账号的所有登录、Token 刷新、Cookie 刷新、商品发布/编辑/擦亮、自动回复、补发货、补评价、监控/线索采集、自动续售、迁移发布 |
| 网络要求 | 冷却结束后优先使用**独立 socks5 代理**（不要与其他账号共用出口 IP） |
| 人工验证 | 仅允许“人工在浏览器完成验证”；不得用自动滑块连续重试 |

### 5.2 冷却期检查清单

- [ ] `xy_accounts.status = disabled`，`disable_reason = 手动禁用`（已确认）
- [ ] websocket 已停止该账号连接（`stop_account` 已执行，日志无该账号心跳）
- [ ] 定时任务已跳过该账号：`token_renewal`、`api_cookie_renew`、`cookies_refresh`、`fetch_items`、`redelivery`、`rate`、`polish`、`listing_monitor`、`lead_comment_scan`、`auto_relist_scan`、`migration_publish`、`dm_send`
- [ ] 冷却期内 `xy_risk_control_logs` 无该账号新增记录
- [ ] 代理配置为独立 IP，未与其他账号共用
- [ ] 未对该账号执行任何自动滑块/自动登录脚本

### 5.3 冷却结束后的恢复步骤

1. **先查日志**：确认冷却期最后一条风控日志距今 ≥ 48 小时，且期间无新增。
2. **确认网络**：为账号配置独立 socks5 代理；`proxy.enabled` 已开启（账号级代理优先于系统代理）。
3. **人工验证优先**：如需登录，使用有头浏览器由人工完成滑块；验证通过后再进入下一步。
4. **重新启用账号**：在“账号管理”页面启用（等价于 `status=active`、清空 `disable_reason`），系统会调用 `start_account` 建立连接。
5. **观察 30 分钟**：只观察心跳、会话与消息推送，不触发批量任务；确认无 `FAIL_SYS_USER_VALIDATE`。
6. **灰度恢复任务**：先恢复自动回复，再逐项恢复定时任务；每项间隔 ≥ 30 分钟观察。
7. **再次触发风控**：立即禁用，冷却时长翻倍（48h → 96h），并检查代理/IP、Cookie 是否被污染。

### 5.4 冷却期禁止动作

- 禁止通过脚本/接口反复调用 Token 刷新或滑块接口。
- 禁止删除/重建账号后立刻重登同一 IP。
- 禁止多个账号共用同一代理出口。
- 禁止在 `failed_captcha` 状态下自动重启账号连接（会形成“失败—重试—再失败”的风控升级循环）。
- 禁止使用相同滑块轨迹重复提交（同点位、同时长、同过冲会被霸屏系统识别）。

## 6. 预防措施

| 措施 | 说明 |
| --- | --- |
| 刷新间隔 | `TOKEN_REFRESH_INTERVAL=72000`（20 小时），与 `websocket/.env` 保持一致 |
| 指数退避 | Token 刷新失败按 10min → 20min → 40min → 60min 退避，成功即重置 |
| 风控共享冷却 | 风控退避状态写入 Redis，全局共享，所有入口统一遵守 |
| 滑块策略 | 保留差异化轨迹（default/cautious/fast/slow），避免固定轨迹；鼠标 `movementX/movementY` 需真实递增 |
| 浏览器指纹 | PC Chrome 使用普通鼠标模式，不使用 `has_touch=True`；Linux Docker 用 Xvfb + headful |
| 并发限制 | `MAX_CAPTCHA_CONCURRENT=3`，避免排队超时与集中触发 |
| 代理策略 | 账号级 socks5 优先；一账号一出口；系统代理仅用于一次性短任务 |
| 自动重连 | `failed_captcha` 时不自动重启账号实例，等待冷却结束 |
